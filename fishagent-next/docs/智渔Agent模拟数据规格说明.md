# 智渔 Agent 模拟数据规格说明

> 文档版本：1.0  
> 基准日期：2026-08-14  
> 适用范围：产品演示、开发联调、自动化测试、Agent 评测、离线降级  
> 核心原则：本说明只定义业务数据、业务状态和场景结果，不规定编程语言、框架、数据库、消息队列或部署方式。

## 1. 文档目的

本说明回答以下问题：

1. 智渔 Agent 原型中有哪些模拟数据，它们分别服务于什么场景。
2. 每类数据的业务字段、单位、状态和值域是什么。
3. 基地、池塘、传感器、设备、告警、任务、巡查和 Agent 对话如何关联。
4. “感知 → 决策 → 执行 → 复核”闭环如何通过数据表达。
5. 如何在任意技术栈中重建一套语义一致、可重复、可验收的模拟数据。
6. 当前原型的两套模拟数据之间有哪些差异，哪些属于历史兼容，哪些应成为后续统一标准。

本文不是数据库设计文档，也不是接口文档。实现方可以使用关系数据库、文档数据库、内存对象、文件、事件流或其他存储方式，只要满足本文的数据语义、关系约束和场景验收条件。

## 2. 术语与数据分层

### 2.1 术语

| 术语 | 含义 |
|---|---|
| 模拟数据 | 为演示、测试或降级而构造的数据，不代表真实生产采集结果 |
| 基线 | 初始化后、任何用户操作和自动调度发生前的数据快照 |
| 场景 | 在基线之上施加的一组有序事件及其预期结果 |
| 权威基线 | 用于完整业务演示和闭环验证的主数据集合 |
| 回退基线 | 主数据服务不可用时，保证界面和 Agent 仍可演示的轻量数据集合 |
| 投影 | 从基础实体计算出的列表、看板、统计或趋势视图 |
| 相对时间 | 以初始化时刻 `T0` 为参照表达的时间，如 `T0-30m` |
| 随机种子 | 控制伪随机序列的固定输入，用于保证每次生成结果一致 |
| 幂等初始化 | 对同一数据集重复执行初始化，不会叠加重复记录，最终状态保持一致 |

### 2.2 数据分层

模拟数据分为四层：

| 层级 | 内容 | 是否可变 | 典型用途 |
|---|---|---:|---|
| 主数据层 | 基地、池塘、传感器、设备 | 低频变化 | 页面基础信息、Agent 查询上下文 |
| 观测层 | 传感器当前值、历史读数、设备状态 | 高频变化 | 监控、趋势、异常检测 |
| 业务层 | 告警、任务、巡查、复核、系统调度配置 | 随场景变化 | 闭环处置、状态追踪 |
| 交互层 | Agent 会话、消息、工具调用、工具结果、执行轨迹 | 随交互变化 | Agent 演示、评测、解释性展示 |

## 3. 数据配置与优先级

当前原型存在两套模拟数据配置，必须明确区分。

### 3.1 配置 A：完整闭环演示基线

配置标识建议使用：`full_closed_loop_v1`。

该配置覆盖：

- 3 个养殖基地；
- 10 个养殖池；
- 54 个传感器；
- 每个传感器 48 条历史读数，共 2,592 条；
- 38 台生产设备；
- 7 条初始告警；
- 8 条初始任务；
- 1 组复核失败闭环数据，额外关联 1 条失败任务；
- 1 条巡查记录；
- 1 份系统调度配置；
- 1 个 Agent 会话和 8 条消息。

这是后续重建时应优先采用的权威业务基线。

### 3.2 配置 B：轻量回退演示基线

配置标识建议使用：`offline_fallback_v1`。

该配置覆盖：

- 3 个逻辑区域名称；
- 8 个养殖池；
- 每个池塘内嵌 4 项当前水质值；
- 18 台设备或设备化传感器；
- 8 条告警；
- 8 条任务；
- 4 个 Agent 会话摘要，其中 2 个包含详细消息；
- 5 类预设 Agent 回答和 1 类默认回答；
- 动态生成的溶解氧趋势和单指标历史曲线。

该配置仅用于接口失败、断网、模型失败或独立 UI 演示。它不是配置 A 的子集，也不能与配置 A 的记录按池号直接合并。

### 3.3 数据优先级

业务消费者选择数据时应遵循：

1. 明确指定的测试场景数据；
2. 配置 A 的当前运行状态；
3. 配置 A 的初始化基线；
4. 配置 B 的回退数据；
5. 空状态。

必须向界面或调用方暴露数据来源，至少区分：

- `simulated_persistent`：可持久化的模拟业务数据；
- `simulated_fallback`：离线或故障回退数据；
- `simulated_generated`：运行时生成的曲线或事件；
- `real`：真实设备或真实业务数据。

不得将模拟数据标记为“实时真实数据”。

## 4. 概念关系

实体关系如下：

```text
养殖基地 1 ── N 养殖池
养殖池   1 ── N 传感器 1 ── N 传感器读数
养殖池   1 ── N 设备
养殖池   1 ── N 告警 1 ── N 处置任务
养殖池   1 ── N 普通任务

系统配置 1 ── N 自动巡查
自动巡查 1 ── N 逐塘巡查明细

Agent 会话 1 ── N 消息
消息 0..1 ── N 工具调用
工具调用 1 ── 0..1 工具结果
```

关键约束：

- 每个池塘必须且只能属于一个基地。
- 每个传感器必须且只能属于一个池塘。
- 每条传感器读数必须引用一个存在的传感器。
- 每台设备必须属于一个池塘。
- 每条告警必须属于一个池塘。
- 任务可以属于某个池塘，也可以是全场级任务。
- 告警触发的处置任务必须引用其来源告警。
- 巡查明细必须引用本次巡查时实际存在的池塘。
- Agent 工具结果必须能追溯到对应工具调用。

## 5. 通用字段约定

### 5.1 标识符

所有实体应具有稳定、唯一、不携带技术实现含义的标识符。

推荐演示数据使用可读标识，例如：

- `farm-linhai`
- `pond-b02`
- `sensor-b02-do`
- `device-b02-aerator-01`
- `alert-b02-low-do-001`
- `task-b02-aeration-001`

要求：

- 同一数据集多次初始化后标识符不变；
- 不使用数组下标作为跨实体引用；
- 显示名称可以修改，标识符不随名称修改；
- 配置 A 与配置 B 的标识符必须带配置命名空间或保证全局不冲突。

### 5.2 时间

- 数据交换时统一使用带时区的 ISO 8601 时间。
- 初始化数据优先使用相对时间，由锚点 `T0` 计算实际时间。
- 业务展示按用户所在时区转换，原始时间语义不变。
- 历史曲线必须按时间升序排列。
- `updated_at` 不得早于 `created_at`。
- `completed_at` 不得早于任务创建时间。
- `reviewed_at` 仅在复核已经发生时存在。

### 5.3 数值和单位

- 数值字段存储纯数值，单位单独表达。
- pH 是无量纲指标，但显示单位可写作 `pH`。
- 温度使用摄氏度 `°C`。
- 溶解氧和氨氮使用 `mg/L`。
- 浊度使用 `NTU`。
- 盐度使用千分比 `‰`。
- 面积必须同时区分基地面积与池塘面积的单位，禁止只写 `area` 而不声明单位。
- 数值默认保留两位小数；面向看板显示时可按指标规则格式化。

### 5.4 可空值

可空不等于零：

- 传感器无读数应为 `null`，不能用 `0` 代替。
- 未排期的任务时间应为 `null`。
- 未完成任务的完成时间应为 `null`。
- 未触发复核的复核时间和复核结果应为 `null`。
- 全场任务的池塘标识应为 `null`。

## 6. 实体数据契约

以下字段名是语义名称，实现方可采用不同的代码命名风格，但不得改变含义。

### 6.1 养殖基地

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 稳定唯一标识 |
| `name` | 字符串 | 是 | 基地名称 |
| `type` | 枚举 | 是 | `indoor`、`outdoor`、`mixed` |
| `address` | 字符串 | 是 | 演示地址，不应对应真实个人地址 |
| `area_value` | 数值 | 是 | 基地面积 |
| `area_unit` | 字符串 | 是 | 当前基线为 `亩` |
| `status` | 枚举 | 是 | `active`、`inactive` |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

### 6.2 养殖池

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 池塘唯一标识 |
| `farm_id` | 字符串 | 是 | 所属基地 |
| `name` | 字符串 | 是 | 业务显示名称 |
| `type` | 枚举 | 是 | `indoor`、`outdoor` |
| `area_m2` | 数值 | 是 | 水面或池体投影面积，平方米 |
| `depth_m` | 数值 | 是 | 平均深度，米 |
| `volume_m3` | 数值 | 是 | 有效水体容积，立方米 |
| `species` | 字符串 | 是 | 当前主要养殖物种 |
| `stock_count` | 整数 | 是 | 存塘或投放数量 |
| `stock_date` | 日期 | 是 | 投放日期 |
| `status` | 枚举 | 是 | `normal`、`warning`、`critical` |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

业务约束：

- `area_m2 > 0`、`depth_m > 0`、`volume_m3 > 0`。
- `stock_count >= 0`。
- `volume_m3` 应与 `area_m2 × depth_m` 大体一致；演示基线采用精确乘积。
- 池塘状态是综合业务状态，不应仅由某一个传感器状态机械替代。

### 6.3 传感器

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 传感器唯一标识 |
| `pond_id` | 字符串 | 是 | 所属池塘 |
| `metric` | 枚举 | 是 | 指标编码 |
| `name` | 字符串 | 是 | 显示名称 |
| `unit` | 字符串 | 是 | 指标单位 |
| `status` | 枚举 | 是 | `online`、`offline`、`error` |
| `last_value` | 数值或空 | 否 | 最新有效值 |
| `observed_at` | 时间或空 | 否 | 最新值采集时间，标准规范要求提供 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

指标编码：

| 指标 | 编码 | 单位 |
|---|---|---|
| 温度 | `temperature` | `°C` |
| 酸碱度 | `ph` | `pH` |
| 溶解氧 | `dissolved_oxygen` | `mg/L` |
| 氨氮 | `ammonia` | `mg/L` |
| 浊度 | `turbidity` | `NTU` |
| 盐度 | `salinity` | `‰` |

### 6.4 传感器读数

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 读数唯一标识 |
| `sensor_id` | 字符串 | 是 | 来源传感器 |
| `value` | 数值 | 是 | 采集值 |
| `observed_at` | 时间 | 是 | 采集时刻 |
| `quality` | 枚举 | 否 | 建议值：`good`、`suspect`、`invalid` |
| `source` | 枚举 | 是 | `simulated` 或 `real` |

约束：同一传感器在同一采集时刻只能有一条有效读数。

### 6.5 设备

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 设备唯一标识 |
| `pond_id` | 字符串 | 是 | 所属池塘 |
| `type` | 枚举 | 是 | 设备类型 |
| `name` | 字符串 | 是 | 设备名称 |
| `status` | 枚举 | 是 | `online`、`offline`、`error` |
| `auto_mode` | 布尔 | 是 | 是否启用自动控制 |
| `last_maintenance_at` | 日期或空 | 否 | 最近维护日期 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

设备类型：

- `aerator`：增氧机；
- `pump`：循环水泵或水泵；
- `feeder`：自动投喂机；
- `heater`：加热器；
- `light`：补光灯或照明灯；
- `filter`：生物过滤器。

传感器不应作为生产设备混入设备清单。若界面需要统一展示，应通过“资产视图”组合，而不是改变传感器的实体类型。

### 6.6 告警

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 告警唯一标识 |
| `pond_id` | 字符串 | 是 | 告警对象 |
| `level` | 枚举 | 是 | `info`、`warning`、`critical` |
| `category` | 枚举 | 是 | `water_quality`、`equipment`、`disease`、`feeding` |
| `title` | 字符串 | 是 | 简短标题 |
| `message` | 字符串 | 是 | 面向用户的完整描述 |
| `trigger_metric` | 字符串或空 | 否 | 触发指标 |
| `trigger_value` | 数值或空 | 否 | 触发时的值 |
| `trigger_unit` | 字符串或空 | 否 | 触发值单位 |
| `trigger_reason` | 字符串或空 | 否 | 可审计的触发原因 |
| `review_status` | 枚举 | 是 | `PENDING`、`PASSED`、`FAILED` |
| `review_due_at` | 时间或空 | 否 | 计划复核时间 |
| `reviewed_at` | 时间或空 | 否 | 实际复核时间 |
| `review_result` | 字符串或空 | 否 | 复核结论 |
| `is_read` | 布尔 | 是 | 是否已读 |
| `is_handled` | 布尔 | 是 | 是否已完成业务处置 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

告警级别语义：

- `info`：提醒或业务信息，不要求立即操作；
- `warning`：存在偏离，应在计划时间内处理；
- `critical`：可能造成生物损失或设备事故，需要立即响应。

### 6.7 任务

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 任务唯一标识 |
| `pond_id` | 字符串或空 | 否 | 空表示全场任务 |
| `source_alert_id` | 字符串或空 | 否 | 来源告警 |
| `title` | 字符串 | 是 | 任务名称 |
| `description` | 字符串或空 | 否 | 操作说明 |
| `type` | 枚举 | 是 | 见下表 |
| `status` | 枚举 | 是 | `pending`、`in_progress`、`completed`、`failed` |
| `priority` | 枚举 | 是 | `low`、`medium`、`high`、`urgent` |
| `scheduled_at` | 时间或空 | 否 | 计划时间 |
| `completed_at` | 时间或空 | 否 | 完成或终止时间 |
| `context` | 字符串或空 | 否 | 决策依据和执行上下文 |
| `result` | 结构化对象或文本 | 否 | 执行结果 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |

任务类型：

- `inspection`：巡检；
- `feeding`：投喂或饲料；
- `treatment`：水质、疾病或设备处置；
- `maintenance`：维护保养；
- `analysis`：统计分析或报告。

任务状态转换：

```text
pending → in_progress → completed
                      ↘ failed
pending ──────────────→ failed
failed  → in_progress           # 人工重试或重新派发时允许
```

禁止无审计信息地把 `failed` 直接改为 `completed`。

### 6.8 巡查记录与逐塘明细

巡查记录字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 巡查唯一标识 |
| `trigger_type` | 枚举 | 是 | `AUTO`、`MANUAL` |
| `start_time` | 时间 | 是 | 开始时间 |
| `end_time` | 时间或空 | 否 | 结束时间 |
| `result` | 枚举或空 | 否 | `ALL_NORMAL`、`HAS_ABNORMAL` |
| `summary` | 字符串或空 | 否 | 汇总说明 |
| `actions_taken` | 整数 | 是 | 实际下发的处置次数 |
| `abnormal_count` | 整数 | 是 | 发现异常的池塘数 |
| `pending_confirmation_count` | 整数 | 是 | 等待人工确认的数量 |
| `details` | 明细数组 | 是 | 逐塘结果 |

逐塘明细字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `pond_id` | 字符串 | 池塘标识 |
| `pond_name` | 字符串 | 当时的池塘名称快照 |
| `status` | 枚举 | `normal`、`action_taken`、`already_running`、`manual_required` |
| `dissolved_oxygen` | 数值或空 | 巡查时的溶解氧快照 |
| `detail` | 字符串 | 判定和处置说明 |

汇总约束：

- `abnormal_count` 等于明细中非 `normal` 且确属水质异常的池塘数量。
- `actions_taken` 只统计真正下发的控制指令，不统计防重复跳过。
- 没有有效读数时，必须增加待确认数，不能判定为正常。

### 6.9 系统调度配置

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 配置标识，基线只有一份默认配置 |
| `next_auto_patrol_time` | 时间 | 是 | 下次自动巡查时间 |
| `auto_patrol_interval_minutes` | 正整数 | 是 | 自动巡查间隔，基线为 30 分钟 |
| `review_delay_minutes` | 正整数 | 是 | 默认处置复核等待，基线为 30 分钟 |
| `safe_dissolved_oxygen_mg_l` | 数值 | 是 | 安全溶氧阈值，统一标准为 5 mg/L |
| `updated_at` | 时间 | 是 | 更新时间 |

### 6.10 Agent 会话、消息与工具调用

会话字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | 字符串 | 是 | 会话标识 |
| `title` | 字符串 | 是 | 会话标题 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 最近活动时间 |

消息字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|

| s4 | 周报生成 | 已生成周度综合分析 | 3 |

详细消息仅为 s1 和 s2 提供。s3、s4 是列表展示占位数据，进入详情时返回空列表。标准实现应补齐详情或明确标记 `detail_available=false`。

Agent 回退回答按关键词选择：

| 意图 | 触发词示例 | 模拟工具调用 | 回答重点 |
|---|---|---|---|
| 检查水质 | 水质、检查水质 | 查询水质 | 5 正常、2 警告、1 严重；B-01 最紧急 |
| 设备控制 | 设备、设备运行状态 | 查询设备 | 18 台设备，3 台离线 |
| 疾病诊断 | 疾病、疾病风险 | 查询水质、分析疾病风险 | B-01 高风险，给出疾病概率和预防建议 |
| 生成报告 | 报告、综合分析报告 | 查询水质、设备、任务并生成报告 | 周度统计与下周重点 |
| 投喂建议 | 投喂、投喂建议 | 查询水质、查询天气 | B-01 暂停，A-02/C-02 减量 |
| 默认问答 | 未命中以上关键词 | 查询知识库 | 汇总当前三个关注点 |

模拟工具耗时为 500–2,500 ms，用于展示执行过程，不代表真实服务性能。

## 9. 动态闭环场景

场景必须在明确基线之上执行，并记录输入、前置状态、事件、预期状态和验收点。

### 9.1 场景 S01：全塘自动巡查

前置条件：

- 系统配置存在；
- 所有池塘至少有一个溶解氧传感器；
- 自动巡查时间已经到期。

执行：

1. 原子性领取本次调度执行权；
2. 读取所有池塘的最新 DO；
3. DO 为空时标记待人工确认；
4. DO 不低于 5 mg/L 时判定正常；
5. DO 低于 5 mg/L 时检查增氧机；
6. 无增氧机则升级人工；
7. 增氧机已在线则记录防重复跳过；
8. 增氧机离线则创建告警、开启设备、创建关联任务并计划复核；
9. 写入逐塘明细和汇总；
10. 计算下次自动巡查时间。

验收：同一调度时间只能生成一条自动巡查记录。

### 9.2 场景 S02：B-01 30 秒低溶氧演示

这是运行时快速演示场景，与配置 A 初始的 B-02 复核失败故事不同。

前置条件：

- 存在名称以 B-01 开头的池塘；
- 该池有 DO 传感器和增氧机；
- 不存在同场景仍待复核的告警。

事件序列：

```text
T0       DO 改为 2.1 mg/L，传感器状态改为 error
T0       增氧机改为 offline，关闭自动模式
T0       创建严重低溶氧告警，复核状态 PENDING
T0       自动开启增氧机并创建关联处置任务
T0+30s   将 DO 固定为 2.2 mg/L，执行复核
T0+30s   复核失败，任务变为 failed
T0+30s   创建“增氧效果异常”二级严重告警，等待人工介入
```

验收：

- 重复点击故障注入不会创建第二条仍待复核的同场景告警；
- 同一告警只创建一条设备控制任务；
- 复核只结算一次；
- 复核失败二级告警只创建一次；
- 所有设备控制都保留触发告警、DO 快照和执行原因。

### 9.3 场景 S03：复核通过

前置条件：存在待复核的低溶氧告警及进行中的关联任务。

事件：在复核前将 DO 调整为不低于 5 mg/L。

预期：

- 告警复核状态变为 `PASSED`；
- 告警标记为已处理；
- 关联进行中任务变为已完成；
- 结果记录复核时的 DO；
- 不产生二级设备告警。

### 9.4 场景 S04：缺少有效读数

事件：目标池塘 DO 最新值为空或质量无效。

预期：

- 不判定为水质正常；
- 巡查明细标记待人工确认；
- 待确认计数增加；
- 不自动下发可能造成风险的设备指令。

### 9.5 场景 S05：缺少增氧设备

事件：DO 低于阈值，但池塘不存在可用增氧机。

预期：

- 创建严重设备类告警；
- 标记无法自动处置；
- 巡查明细为 `manual_required`；
- 不伪造设备控制成功；
- 重复巡查不重复创建相同未处理告警。

### 9.6 场景 S06：防重复控制

事件：DO 低于阈值，但增氧机已经在线，或同一来源告警已有控制任务。

预期：

- 不重复下发开启指令；
- 记录“已在目标状态”或“已有处置记录”；
- `actions_taken` 不增加；
- 原有任务和上下文保持可追溯。

## 10. 面向消费者的数据投影

实现方可以自由设计接口，但应能生成以下业务投影。

### 10.1 监控总览

- 池塘总数、室内数、室外数；
- 未读或活跃告警数、严重告警数；
- 今日任务总数及各状态数量；
- 设备总数、在线数、在线率；
- 最新巡查、下次巡查时间和待复核数。

所有统计必须来自同一个数据配置和同一个一致性快照。禁止用配置 B 计算池塘数、同时用配置 A 计算告警数。

### 10.2 池塘卡片

- 池塘名称、基地、类型、物种、存量、面积；
- 综合状态；
- 温度、pH、DO、氨氮最新值；
- 最新异常或告警摘要。

### 10.3 设备管理

- 设备名称、池塘、类型、连接或运行状态、自动模式；
- 最近维护时间；
- 设备状态切换产生的任务和上下文。

### 10.4 告警中心

- 告警级别、类别、池塘、标题、时间；
- 已读、已处理、复核状态；
- 触发值、触发原因和关联任务；
- 复核结果和二级升级告警。

### 10.5 Agent 上下文

Agent 可读取：

- 当前池塘和水质快照；
- 设备状态；
- 活跃告警；
- 任务；
- 历史趋势；
- 用户授权和操作上下文。

Agent 不应直接修改主数据。设备控制和任务变更必须通过受控业务动作完成并留下审计记录。

## 12. 初始化、重置和时间推进

### 12.1 初始化

标准初始化应：

1. 验证数据契约版本；
2. 验证所有跨实体引用；
3. 使用固定锚点和随机种子解析生成数据；
4. 以数据集标识建立隔离范围；
5. 幂等写入主数据；
6. 写入初始场景状态；
7. 输出各实体数量和校验摘要。

### 12.2 重置

重置只能清理指定模拟数据集生成的数据，不得删除真实数据或其他数据集。

重置后应恢复到本文对应配置的精确基线，包括设备状态、告警状态、任务状态、调度时间和 Agent 会话。

### 12.3 时间推进

测试和演示不应依赖真实等待 30 分钟。场景执行器应支持逻辑时钟：

- `advance +30s`：触发快速演示复核；
- `advance +30m`：触发常规复核或下一次巡查；
- `set T0`：重置到锚点时间。

逻辑时钟推进必须产生与真实时间到期相同的业务结果。

## 13. 确定性与随机数据

模拟数据必须可复现。

要求：

- 同一数据版本、锚点和随机种子生成完全相同的值；
- 趋势曲线在页面刷新后保持稳定；
- 自动化测试不得依赖未固定的随机值；
- 异常点必须由场景显式定义，不能期待随机数“碰巧异常”；
- 随机数据只用于填充非关键正常波动。

关键告警、阈值、设备离线清单、任务状态和 Agent 结论必须是确定性的。

## 14. 数据一致性规则

### 14.1 基本一致性

- 池塘引用的基地必须存在。
- 传感器、设备、告警引用的池塘必须存在。
- 关联告警的任务必须与告警属于同一池塘，除非明确为全场协调任务。
- 传感器 `last_value` 应等于该传感器最新一条有效历史读数，场景覆盖时除外。
- 告警消息中的数值、结构化触发值和 Agent 回答中的数值必须一致。
- 看板统计必须能从明细重新计算。
- 会话摘要的消息数必须等于实际可读取的消息数，或明确标记仅为占位摘要。

### 14.2 闭环一致性

- 自动处置告警必须有触发指标、触发值、单位和原因。
- 自动设备动作必须产生任务或等价审计记录。
- 关联任务必须保存来源告警和执行上下文。
- 复核通过时告警已处理、任务完成。
- 复核失败时任务失败，并产生一次人工升级通知或告警。
- 防重复跳过不能计为实际执行。

### 14.3 安全一致性

- 无有效读数不自动判定正常。
- 无设备不伪造控制结果。
- 未经授权的高风险动作不应在对话数据中显示为已执行。
- 模拟执行必须清晰标记，避免误认为连接了真实设备。

## 16. 当前原型的已知偏差

以下内容是对现状的客观记录，不是后续标准。

### 16.1 两套数据在同一页面混用

当前监控总览和池塘列表使用配置 B 的 8 池数据，而告警、任务、设备和巡查可读取配置 A 的持久化数据。结果可能出现：

- 看板显示 8 个池塘，但后端实际有 10 个；
- B-01 在回退数据中是草鱼严重低溶氧池，在完整基线中是大黄鱼正常池；
- B-02 在回退数据中正常，在完整基线中承担严重低溶氧闭环；
- 同一页面的统计与明细不能互相校验。

后续应让页面选择单一数据配置，并在请求链路中显式传播 `dataset_id`。

### 16.2 阈值口径不一致

- 完整闭环以 5 mg/L 作为 DO 安全阈值；
- 部分回退告警文本以 3 mg/L 作为安全阈值；
- 部分回退回答又要求恢复到 5 mg/L。

标准统一为 5 mg/L；若不同物种需要不同阈值，应建立阈值策略数据，而不是在文本中硬编码。

### 16.3 B-01 与 B-02 故事不一致

- 配置 A 初始故事：B-02 低溶氧并复核失败；
- 配置 B 回退故事：B-01 低溶氧；
- 30 秒动态演示：B-01 故障注入。

建议后续选择一个“主演示池”，或显式命名为不同场景，避免评委认为 Agent 前后矛盾。

### 16.4 随机值不可复现

当前传感器、设备在线状态和趋势曲线使用未固定随机值。刷新或重新初始化后结果可能变化，影响截图、测试和 Agent 结论。

标准要求固定随机种子，并将关键异常显式写入场景。

### 16.5 初始化非幂等

当前完整基线使用追加式创建。若在已有数据上再次初始化，会重复创建基地、池塘和业务数据。

标准要求按 `dataset_id + stable_id` 幂等写入，或先安全重置指定数据集。

### 16.6 关键告警与传感器值可能不一致

完整基线为 B-02 创建 2.1 mg/L 低溶氧告警，但初始化时没有强制把 B-02 DO 传感器最新值设置为 2.1。其最新值可能仍来自正常区间随机生成。

标准要求告警触发值、传感器最新值、历史最后一点、任务上下文和 Agent 回答一致。

### 16.7 设备名称可能重复

当前完整基线按池号第一段生成设备名称，A-01 与 A-02、B-01 与 B-02 可能产生相同名称。标准名称必须包含完整池号和同类设备序号。

### 16.8 历史数据说明偏差

当前初始化日志称“48小时历史数据”，实际是 48 个半小时点，覆盖约 24 小时。标准应写作“24 小时、每 30 分钟一条、共 48 条”。

### 16.9 当前运行快照不是干净基线

2026-08-14 检查现有演示数据时，持久化快照包含：

- 3 个基地、10 个池塘、54 个传感器、2,592 条读数、38 台设备；
- 9 条告警、9 条任务、18 条巡查记录；
- 1 份系统配置、1 个 Agent 会话、8 条消息。

多出的告警和巡查来自运行时演示与自动调度。验收初始化数量时必须使用干净重置后的数据集，不能直接以该运行快照为基线。

## 17. 后续统一建议

按优先级建议：

1. 将配置 A 定为唯一权威演示数据，配置 B 只保留为明确的离线配置。
2. 为两套配置增加 `dataset_id`、版本、锚点和随机种子。
3. 统一 DO 安全阈值和主演示池故事。
4. 让所有页面投影来自同一数据配置。
5. 将关键场景从代码逻辑中抽为可读的场景数据。
6. 实现指定数据集的幂等初始化、重置和数量校验。
7. 为每次截图、比赛演示和 Agent Eval 固定数据版本。
8. 在界面显著标注“模拟数据”或“离线演示”。

## 18. 完成定义

一套模拟数据实现只有同时满足以下条件，才算符合本说明：

- 数据实体和关系完整；
- 数量、单位、枚举和值域通过校验；
- 同一业务事实在传感器、告警、任务、巡查和 Agent 回答中一致；
- 初始化和重置可重复；
- 关键场景可确定性复现；
- 闭环动作可追溯且具备防重复保护；
- 真实数据与模拟数据有明确边界；
- 任意实现技术替换后，业务语义和验收结果不变。

这份规格的最终目标不是“造一些看起来像真的数字”，而是提供一套可解释、可复现、可验证的业务世界，让界面、Agent、自动化任务和测试围绕同一事实运行。
